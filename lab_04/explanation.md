# Лабораторная № 4. Полный разбор шести объектов

## 0. Что мы делаем и как читать код

В исходной формулировке лабораторной указан SQL CLR. CLR — среда выполнения
.NET, которую Microsoft SQL Server использует для вызова кода, например C#.
В этой работе используется разрешённый вариант **PostgreSQL + Python**.
Здесь Python исполняется внутри PostgreSQL через расширение **PL/Python**.
Это другой механизм, который позволяет разобрать те же категории объектов.

Соответствие заданию:

| Категория | Объект в нашей работе | Что получается при вызове |
| --- | --- | --- |
| Скалярная функция | `sc1.get_total_price_py` | Одно число |
| Агрегат | `sc1.total_arrival_sum_py` | Одно число для набора строк или группы |
| Табличная функция | `sc1.get_arrivals_by_product_py` | Набор строк |
| Хранимая процедура | `sc1.increase_product_price_py` | Изменённые цены в таблице |
| Триггер | `increase_product_price_trigger_py` | Автоматическая запись в журнал |
| Пользовательский тип | `sc1.product_balance_py` | Одно значение с несколькими полями |

Все определения находятся в `data_modules.sql`. Отдельные вспомогательные
функции и таблица журнала необходимы для работы этих шести категорий.
То есть SQL-объектов физически больше шести: например, триггер вызывает
триггерную функцию, а агрегат вызывает функцию накопления.

У тебя уже есть база `warehouse`, схема `sc1` и таблицы склада:

- `product` — товары;
- `arrival_item` — позиции поступлений, в том числе `product_id`, `quantity`, `unit_price`;
- `expense_item` — позиции расходов с товаром и количеством.

Суффикс `_py` означает, что это версия объекта для четвёртой лабораторной.
Старые функции и процедуры из третьей лабораторной остаются в базе.

### Общая форма функции

```sql
create or replace function sc1.имя(параметры)
returns тип_результата
as $$
# Здесь обычный Python, включая значимые отступы.
return результат
$$ language plpython3u;
```

`create or replace` создаёт объект или заменяет его определение.
Внешняя оболочка — SQL: имя, параметры, возвращаемый тип и язык.
Между `$$` находится тело на Python. `$$` ограничивает строку с кодом,
поэтому внутренние одинарные и двойные кавычки не приходится экранировать.

В отличие от прошлой лабы, внутри Python нет `begin`, `end` и `return query`.
Отступы внутри `if` имеют значение. Параметры SQL-функции уже доступны
в Python по своим именам; писать `def` не требуется.

### Как сопоставляются типы

| PostgreSQL | Python внутри PL/Python |
| --- | --- |
| `integer`, `bigint` | `int` |
| `numeric` | `Decimal` |
| `text`, `varchar` | `str` |
| `NULL` | `None` |
| Составной аргумент | Отображение, поля можно читать по именам |

Для денег у нас `numeric`, поэтому код не переводит цены в `float`.
Обычные двоичные числа с плавающей точкой могут неточно представлять
десятичные дроби. Здесь стоимость считается через `Decimal`.
В примерах используются масштабы величин существующей учебной базы;
произвольную точность PostgreSQL `numeric` Python-контекст Decimal автоматически
не повторяет: стандартная точность арифметики Decimal — 28 значащих цифр.

`strict` означает: если хотя бы один аргумент `NULL`, PostgreSQL не вызывает
тело функции. Скалярная функция возвращает `NULL`, функция, возвращающая
набор строк, — пустой набор.

`immutable` ставится у чистых вычислений: одинаковые аргументы дают одинаковый
результат, чтения таблиц нет. `stable` стоит у функций чтения таблиц: в рамках
одного SQL-оператора они используют согласованный снимок данных.
`stable` не означает, что PostgreSQL навсегда запоминает результат.

## 1. Скалярная функция `get_total_price_py`

### Задача

Получить стоимость одной позиции поступления:

```text
стоимость = цена за единицу × количество
```

Например, четыре болта по 12.50 стоят 50.

### Код

```sql
create or replace function sc1.get_total_price_py(p_price numeric, p_quantity integer)
returns numeric
as $$
return p_price * p_quantity
$$ language plpython3u immutable strict;
```

### Разбор

`p_price` — цена. `p_quantity` — количество. Префикс `p_` помогает отличать
параметры от названий столбцов.

`returns numeric` означает, что один вызов возвращает одно число.
Python получает цену как `Decimal`, количество как целое число,
перемножает их и возвращает результат PostgreSQL.

Здесь не нужен `plpy`, потому что функция ничего не читает и не меняет в БД.
Флаги `immutable strict` подходят, потому что результат зависит только от
параметров и неизвестная цена или неизвестное количество дают неизвестную
стоимость.

### Вызов

```sql
select sc1.get_total_price_py(12.5, 4);  -- 50
select sc1.get_total_price_py(12.5, 0);  -- 0
select sc1.get_total_price_py(null, 4);  -- NULL
```

Можно вызвать функцию для каждой строки таблицы:

```sql
select id, quantity, unit_price,
       sc1.get_total_price_py(unit_price, quantity) as total_price
from sc1.arrival_item;
```

Если поступлений 2000, запрос вернёт 2000 строк с отдельно вычисленной
стоимостью. Скалярная функция сама по себе строки не объединяет.

### Что сказать на защите

«Скалярная функция принимает цену и количество и возвращает одно числовое
значение — их произведение. Её можно использовать в выражениях SELECT.
Тело написано на Python, типы параметров и результата задаёт PostgreSQL».

## 2. Агрегат `total_arrival_sum_py`

### Задача

Посчитать общую стоимость нескольких позиций поступления. Для каждой строки
нужно умножить цену на количество, затем сложить результаты.

Это учебный аналог `sum(unit_price * quantity)`, реализованный через Python.
В прикладном запросе готовый `sum` был бы достаточен; здесь цель — понять
устройство пользовательского агрегата.

### Из чего состоит агрегат

Есть функция перехода, которая обрабатывает очередную строку:

```sql
create or replace function sc1.arrival_sum_step_py(
    p_sum numeric, p_price numeric, p_quantity integer
)
returns numeric
as $$
if p_price is None or p_quantity is None:
    return p_sum

return p_sum + p_price * p_quantity
$$ language plpython3u immutable;
```

И есть определение самого агрегата:

```sql
create or replace aggregate sc1.total_arrival_sum_py(numeric, integer) (
    sfunc = sc1.arrival_sum_step_py,
    stype = numeric,
    initcond = '0'
);
```

### Разбор

`sfunc` — функция перехода, то есть функция обновления состояния.
`stype` — тип промежуточного состояния. У нас состояние — накопленная сумма.
`initcond` — начальное значение состояния: ноль.

У агрегата два входных аргумента: цена и количество. У функции перехода
их три, потому что первым PostgreSQL дополнительно передаёт текущую сумму.

Для строк `(12.5, 4)` и `(7, 10)` выполнение выглядит так:

```text
Начальное состояние: 0
Первая строка:       0 + 12.5 × 4 = 50
Вторая строка:       50 + 7 × 10 = 120
Итоговый результат:  120
```

Цикл по строкам организует PostgreSQL. Писать Python-цикл внутри функции
накопления не нужно. Достаточно обработать одну очередную строку.

Если цена или количество равны `NULL`, в Python приходит `None`.
Стоимость такой строки неизвестна, поэтому строка пропускается: состояние
возвращается без изменения. Мы не ставим `strict` на функцию перехода,
а явно задаём эту обработку в коде.

Отдельная финальная функция не нужна: накопленное число уже является ответом.

### Вызов

```sql
select sc1.total_arrival_sum_py(unit_price, quantity)
from sc1.arrival_item;
```

Один результат на всю таблицу. Чтобы получить результат по каждому товару:

```sql
select product_id,
       sc1.total_arrival_sum_py(unit_price, quantity) as total_sum
from sc1.arrival_item
group by product_id;
```

При `group by` для каждой группы поддерживается отдельное состояние.

### Пустой набор и NULL

Если строк вообще нет либо во всех строках хотя бы один аргумент `NULL`,
ответ равен **0**. Это следствие `initcond = '0'`.
Встроенный `sum` для пустого набора возвращает `NULL`, поэтому в общем
случае наш результат сравнивается с `coalesce(sum(...), 0)`.

### Что сказать на защите

«Агрегат сворачивает множество строк в одно значение. PostgreSQL хранит
состояние типа numeric, начиная с нуля, и для каждой строки вызывает
Python-функцию, которая добавляет стоимость позиции».

## 3. Табличная функция `get_arrivals_by_product_py`

### Задача

Передать id товара и получить все его позиции поступления. Результат имеет
столбцы `arrival_item_id`, `quantity`, `unit_price`.

### Код

```sql
create or replace function sc1.get_arrivals_by_product_py(p_product_id integer)
returns table (
    arrival_item_id integer,
    quantity integer,
    unit_price numeric
)
as $$
plan = plpy.prepare("""
    select ai.id as arrival_item_id, ai.quantity, ai.unit_price
    from sc1.arrival_item as ai
    where ai.product_id = $1
    order by ai.id
""", ["integer"])

return plpy.execute(plan, [p_product_id])
$$ language plpython3u stable strict;
```

### Разбор `plpy`

`plpy` — предоставляемый PostgreSQL модуль для взаимодействия с базой
из PL/Python. Импортировать его не нужно. Отдельное подключение через
`psycopg` также не требуется: код уже работает внутри сервера.

`plpy.prepare` подготавливает SQL-запрос с типизированными параметрами.
Здесь `$1` — место для первого аргумента. Список `["integer"]` задаёт его
тип. Это синтаксис параметров запроса PostgreSQL, а не переменная Python.

`plpy.execute(plan, [p_product_id])` выполняет запрос, подставляя переданный
id. Значение передаётся отдельно от текста SQL. Не нужно склеивать строку
запроса через `+ str(p_product_id)`.

Результат `plpy.execute` содержит строки, доступные как отображения по именам
столбцов. PL/Python умеет возвращать такой итерируемый результат в качестве
набора строк. Имена `arrival_item_id`, `quantity`, `unit_price` согласованы
с объявлением `returns table`.

Тройные кавычки `"""` создают многострочную строку Python: в ней находится
обычный SQL-запрос. Тело функции при этом остаётся Python-кодом.

### Вызов

```sql
select * from sc1.get_arrivals_by_product_py(1);
```

Вызываем в секции `from`, потому что хотим обращаться к результату как
к таблице. К нему можно добавить фильтр, сортировку или соединение:

```sql
select *
from sc1.get_arrivals_by_product_py(1)
where quantity > 5
order by arrival_item_id;
```

Если поступлений нет или id равен `NULL`, результат — пустой набор.
Порядок итогового результата гарантирует внешний `order by`, когда он нужен.

### Отличие от скалярной функции

Скалярная функция отвечает «сколько стоит эта позиция?» и возвращает число.
Табличная отвечает «какие поступления были у товара?» и возвращает строки.
Новая постоянная таблица при вызове не создаётся.

### Что сказать на защите

«Табличная функция возвращает набор строк заранее объявленной структуры.
Из Python она выполняет параметризованный SQL-запрос через plpy и возвращает
его строки PostgreSQL».

## 4. Процедура `increase_product_price_py`

### Задача

Изменить цены всех позиций поступления определённого товара на заданный
процент. Например, при `10` цена увеличивается в `1.1` раза.

### Как работает тело процедуры

Сначала проверяются аргументы:

```python
if p_product_id is None or p_percent is None:
    plpy.error("Товар и процент должны быть указаны", sqlstate="22004")

if not p_percent.is_finite() or p_percent <= -100:
    plpy.error("Процент должен быть конечным числом больше -100", sqlstate="22023")
```

Процедура получает процент как `Decimal`. `is_finite()` отбрасывает `NaN`
и бесконечности. `-100%` обнуляет цену, а меньший процент делает её
отрицательной, поэтому такие аргументы отклоняются. В существующей базе
цены должны быть положительными.

`plpy.error` прерывает выполнение с ошибкой PostgreSQL. `sqlstate` — код
категории ошибки: `22004` для недопустимого `NULL`, `22023` для неверного
значения параметра. В тестах по этим кодам проверяется ожидаемая ошибка.

Затем подготавливается и выполняется обновление:

```python
plan = plpy.prepare("""
    update sc1.arrival_item
    set unit_price = unit_price * (1 + $2 / 100)
    where product_id = $1
""", ["integer", "numeric"])

result = plpy.execute(plan, [p_product_id, p_percent])
plpy.notice("Обновлено строк: " + str(result.nrows()))
```

`$1` — id товара, `$2` — процент. Обновление выполняется сразу для всех
подходящих строк. Курсор и ручной цикл здесь не нужны.

Здесь `$2 / 100` вычисляет SQL, а не Python. В запросе `$2` имеет тип
`numeric`, поэтому это десятичное деление.

Примеры множителя:

| Процент | Множитель | Что произойдёт |
| --- | --- | --- |
| `10` | `1.1` | Повышение на 10% |
| `0` | `1` | Цена не меняется |
| `-20` | `0.8` | Снижение на 20% |

Несмотря на имя `increase`, процедура допускает и снижение в пределах
`-100 < процент < 0`. Это явно заданное поведение.

`result.nrows()` сообщает число обновлённых строк. `plpy.notice` выводит
сообщение, но не возвращает таблицу. Если подходящих строк нет, будет
сообщение `Обновлено строк: 0`.

Столбец `unit_price` имеет тип `numeric(10, 3)`: PostgreSQL округляет
результат до трёх знаков. Если новое значение не помещается в этот тип
или после округления нарушает ограничение положительной цены, оператор
завершится ошибкой, изменения этого оператора отменятся.

### Вызов и безопасная демонстрация

```sql
begin;

select id, unit_price from sc1.arrival_item where product_id = 1;
call sc1.increase_product_price_py(1, 10);
select id, unit_price from sc1.arrival_item where product_id = 1;

rollback;
```

`call` вызывает процедуру. Сама процедура не фиксирует транзакцию.
Здесь `rollback` возвращает цены к исходным. Если вызвать её вне явного
`begin` в обычном psql с автофиксацией, успешные изменения сохранятся.
Повторный вызов на 10% снова повысит уже изменённую цену.

### Что сказать на защите

«Процедура предназначена для действия: она изменяет таблицу. Вызывается
через CALL, принимает id товара и процент, проверяет аргументы и выполняет
UPDATE из Python. Результат как число или таблицу она не возвращает».

## 5. Триггер `increase_product_price_trigger_py`

### Задача

Автоматически сохранять информацию об изменении цены: какая позиция,
какой товар, старая цена, новая цена и время изменения.

В отличие от третьей лабы, здесь уведомление не только выводится на экран:
запись хранится в таблице `sc1.product_price_log_py`.

### Из чего состоит решение

Есть таблица журнала:

```text
id | arrival_item_id | product_id | old_price | new_price | changed_at
```

`id` генерируется автоматически через `generated always as identity`.
`changed_at` получает `current_timestamp` по умолчанию. В PostgreSQL это
время начала текущей транзакции, поэтому несколько записей одной транзакции
могут иметь одинаковое время.

Есть Python-функция `sc1.log_increase_product_price_py()`, которая заполняет
журнал. И есть сам триггер, определяющий, когда вызвать эту функцию:

```sql
create or replace trigger increase_product_price_trigger_py
after update of unit_price on sc1.arrival_item
for each row
when (old.unit_price is distinct from new.unit_price)
execute function sc1.log_increase_product_price_py();
```

### Разбор определения триггера

`after` — действие выполняется после обновления строки.
Это ещё не означает фиксацию транзакции: журнал и обновление остаются
частями одной транзакции.

`update of unit_price` — триггер рассматривается, когда столбец цены
указан в обновлении. Обновление только количества его не вызывает.

`for each row` — отдельный вызов для каждой подходящей строки.
Если процедура обновляет две цены, функция триггера вызывается дважды.

`when (old.unit_price is distinct from new.unit_price)` — дополнительная
проверка, что значение действительно изменилось. Благодаря ей запрос
`set unit_price = unit_price` не создаёт лишних записей.
`is distinct from` корректно сравнивает значения и при наличии `NULL`.

### Что такое `TD`

В триггерной функции PL/Python PostgreSQL автоматически предоставляет
словарь `TD` с данными события:

```python
old_row = TD["old"]
new_row = TD["new"]
```

Для нашего `UPDATE` `TD["old"]` — строка до изменения,
`TD["new"]` — строка после изменения. Поэтому:

```python
old_row["unit_price"]  # старая цена
new_row["unit_price"]  # новая цена
new_row["id"]          # id позиции поступления
new_row["product_id"]  # id товара
```

Триггерная функция вставляет эти значения в журнал через параметризованный
`insert`. Последнее `return None` подходит для `AFTER`-триггера:
он уже не изменяет новую строку. Здесь не нужно писать `return new`,
как в твоих триггерах PL/pgSQL.

### Как проверить

```sql
begin;

call sc1.increase_product_price_py(1, 10);
select * from sc1.product_price_log_py where product_id = 1 order by id;

rollback;
```

Триггер работает и при обычном `update`, без вызова процедуры.
Приложению не нужно отдельно вызывать функцию журналирования.

Если операция откатывается, вставка в журнал также откатывается.
Поэтому это журнал успешных изменений внутри БД, а не независимая запись
всех неудачных попыток изменения. Счётчик identity при откатах может
оставлять пропуски в номерах — это нормально.

Если вставка в журнал завершится ошибкой, обновление цены тоже не сможет
успешно завершиться: обе операции выполняются вместе.

### Что сказать на защите

«Триггер автоматически запускает Python-функцию после фактического изменения
цены каждой строки. Старая и новая строки доступны через TD. Функция
записывает изменение в журнал в той же транзакции».

## 6. Тип `product_balance_py` и функция `get_product_balance_py`

### Задача

Хранить описание остатка товара в одном структурированном значении:

```text
id товара, количество прихода, количество расхода, остаток
```

В PostgreSQL для этого подходит пользовательский составной тип.
Тип объявляется SQL-командой, а его значение рассчитывает Python-функция.
Это именно составной тип PostgreSQL, а не Python-класс и не CLR-тип.

### Определение типа

```sql
create type sc1.product_balance_py as (
    product_id integer,
    arrived_quantity bigint,
    spent_quantity bigint,
    balance bigint
);
```

`create type` создаёт описание структуры. Постоянная таблица с данными
при этом не создаётся. Тип можно использовать для столбца таблицы,
переменной, параметра или результата функции.

Для суммарных количеств используется `bigint`: сумма многих `integer`
может выйти за диапазон одного `integer`.

В `data_modules.sql` определение обёрнуто в блок `do`, который сначала
проверяет наличие типа в системных каталогах. У `create type` нет варианта
`or replace`, поэтому проверка позволяет повторить установку с той же
структурой типа. Этот блок написан на стандартном PL/pgSQL и занимается
только созданием типа, а не обработкой складских данных.

### Функция, возвращающая тип

```sql
create or replace function sc1.get_product_balance_py(p_product_id integer)
returns sc1.product_balance_py
...
```

Обрати внимание: `returns` содержит имя нашего типа. Значит, один вызов
возвращает одно составное значение, а не произвольный набор строк.

Функция выполняет запрос, который для товара отдельно считает:

```sql
select coalesce(sum(ai.quantity), 0)
from sc1.arrival_item as ai
where ai.product_id = p.id
```

И аналогично считает расход по `expense_item`.

`coalesce(..., 0)` заменяет `NULL` от суммы по пустой таблице на ноль.
Существующий товар без движений должен иметь приход 0, расход 0 и остаток 0.

Поступления и расходы суммируются **отдельно**. Если сразу соединить
несколько поступлений с несколькими расходами одного товара, строки
могут перемножиться, и суммы окажутся завышенными.

После выполнения запроса:

```python
rows = plpy.execute(plan, [p_product_id])
if len(rows) == 0:
    return None
```

Если самого товара нет в `product`, функция возвращает SQL `NULL`.
Это отличается от существующего товара без движений, для которого
возвращается заполненная структура с нулевыми количествами.

Если товар найден, Python возвращает словарь:

```python
row = rows[0]
return {
    "product_id": row["id"],
    "arrived_quantity": row["arrived_quantity"],
    "spent_quantity": row["spent_quantity"],
    "balance": row["arrived_quantity"] - row["spent_quantity"]
}
```

Ключи словаря совпадают с полями типа. PL/Python преобразует этот словарь
в значение `sc1.product_balance_py`.

Остаток — учётный: сумма поступлений минус сумма расходов. Данные
`inventory.actual_quantity` здесь не используются: это фактически
пересчитанное количество, которое может отличаться от учётного.
Учитываются все движения товара в базе без фильтра по дате и месту хранения.
Если расход больше прихода, остаток будет отрицательным.

### Вызовы

Получить одно составное значение:

```sql
select sc1.get_product_balance_py(1);
-- Например: (1,14,3,11). Для твоего товара числа зависят от данных.
```

Развернуть поля в отдельные столбцы:

```sql
select * from sc1.get_product_balance_py(1);
```

Получить только остаток:

```sql
select (sc1.get_product_balance_py(1)).balance;
```

Внешние скобки нужны для обращения к полю составного результата.

Создать значение вручную:

```sql
select row(1, 14, 3, 11)::sc1.product_balance_py;
```

Пример столбца с нашим типом без постоянных изменений в базе:

```sql
begin;
create temporary table balance_example(value sc1.product_balance_py);
insert into balance_example values (sc1.get_product_balance_py(1));
select (value).* from balance_example;
rollback;
```

Сам составной тип описывает поля, но не заставляет `balance` равняться
`arrived_quantity - spent_quantity`: при ручном конструировании можно
записать несогласованные числа. В нашей функции формула рассчитывается
автоматически. Сохранённое значение также не пересчитывается само,
когда позднее меняются движения товара.

### Что сказать на защите

«Я создал составной пользовательский тип для id товара, прихода, расхода
и остатка. Python-функция отдельно суммирует приходы и расходы, вычисляет
разницу и возвращает словарь, который PL/Python преобразует в этот тип.
Тип можно использовать в столбцах таблиц и разбирать на отдельные поля».

## 7. Как установить и проверить работу

Из терминала Ubuntu:

```bash
cd /home/artyom/repositories/bmstu_db/lab_04
psql -X -v ON_ERROR_STOP=1 -d warehouse -f install.sql
psql -X -v ON_ERROR_STOP=1 -d warehouse -f tests.sql
```

`-d warehouse` выбирает базу. `-f` выполняет файл. `-X` исключает влияние
личного стартового файла psql. `ON_ERROR_STOP=1` останавливает выполнение
при первой ошибке вместо продолжения с частично выполненными командами.

`install.sql` одной транзакцией выполняет `setup.sql` и `data_modules.sql`.
Команда `\ir` ищет включаемые файлы относительно самого `install.sql`.
Поэтому скрипт можно вызвать и по абсолютному пути.

На новой Ubuntu с PostgreSQL 14 нужен пакет:

```bash
sudo apt install postgresql-plpython3-14
```

Затем расширение подключается **внутри конкретной базы**:

```sql
create extension if not exists plpython3u;
```

Имя `plpython3u` означает Python 3 и untrusted-язык. В PostgreSQL создание
таких функций доступно суперпользователю. Это не значит, что каждый вызов
функции требует входа от системного пользователя root. В твоей базе роль
`artyom` уже является суперпользователем PostgreSQL.

В `tests.sql` создаются собственные строки с отрицательными id, чтобы
получить заранее известные результаты, независимо от случайного заполнения:

| Проверка | Ожидаемое значение |
| --- | --- |
| Первая стоимость | `12.5 × 4 = 50` |
| Общая стоимость | `12.5 × 4 + 7 × 10 = 120` |
| Табличная функция | 2 позиции поступления |
| Повышение на 10% | Цены `13.750` и `7.700` |
| Журнал после повышения | 2 записи со старыми и новыми ценами |
| Дополнительный обычный UPDATE | Ещё 1 запись журнала |
| Остаток | Приход `14`, расход `3`, остаток `11` |

Также проверяются `NULL`, нулевое количество, пустой набор, существующий
товар без движений, отсутствующий товар, обновление без изменения цены,
ошибочный процент и сохранение составного типа в столбце.

В тестовых блоках используется PL/pgSQL-команда `assert`: если условие
ложно, тест останавливается с ошибкой. `set local plpgsql.check_asserts = on`
включает проверки на время тестовой транзакции.

В конце выполняется `rollback`: тестовые данные, изменённые цены и записи
журнала откатываются. Установленные определения функций, процедуры,
агрегата, триггера и типа остаются, потому что они созданы отдельным запуском.

## 8. Короткие ответы для защиты

**Чем функция отличается от процедуры?** Функцию вызывают в SQL-выражении,
она возвращает значение или набор. Нашу процедуру вызывают через `call`,
она выполняет изменение цен. В PostgreSQL функции тоже технически могут
изменять данные, поэтому «функция никогда не меняет таблицы» — неверное правило.

**Чем агрегат отличается от скалярной функции?** Один вызов скалярной
функции обрабатывает переданные аргументы и возвращает одно значение.
Агрегат получает набор строк, поддерживает состояние и выдаёт один результат
на набор или на каждую группу.

**Зачем нужен триггер, если есть процедура?** Цену могут изменить обычным
`update`, минуя процедуру. Триггер реагирует на событие в таблице независимо
от того, какой подходящий запрос его вызвал.

**Зачем нужен пользовательский тип?** Он задаёт общую структуру связанного
значения: здесь это сведения об остатке. Такой тип можно переиспользовать
в разных функциях, переменных и столбцах.

**Почему не отдельный Python-скрипт?** Тела функций выполняются внутри
PostgreSQL. Мы вызываем их обычным SQL, а PostgreSQL сам передаёт аргументы
в Python и преобразует результат обратно.

**Это точно SQL CLR?** Нет: реализация выполнена на согласованной связке
PostgreSQL + PL/Python. CLR относится к .NET и Microsoft SQL Server.
В отчёте корректно назвать работу «аналоги объектов SQL CLR на PL/Python».
